# On-Device Deployment and New-Device Onboarding

Platform adaptation data is centralized in the device section of `topology/profiles.yaml` (port-name mapping,
diagnostic channel, default VLAN, loopback mode, capability gating); environment variables serve only as
temporary overrides. The target DUT is specified by `DUT_HOST` / `DUT_USERS` (comma-separated candidates,
falling back to `DUT_USER`) / `DUT_PASS` (defaults in `tools/dutssh.py`; credentials default to the SONiC
factory admin).

## 0. Prerequisites

- The DUT is a healthy SONiC: swss/syncd RUNNING, and `show interfaces status` shows ports.
- You can SSH from the build machine to the DUT (`tools/dutssh.py`, pexpect + system ssh, password login).
- Before a full production run, it's recommended to reboot or `config reload` back to a clean device state to
  avoid interference from historical residue.

## 1. Dependencies

The DUT usually has scapy installed; pytest most likely not. When the DUT has no public-internet access but can
reach the build machine, use offline installation:

```bash
# Build machine: download wheels and start an http server (pytest is pure Python, portable across minor versions)
pip3 download pytest -d wheelhouse
( cd wheelhouse && python3 -m http.server 8088 & )
# DUT: install offline
sudo pip3 install --no-index --find-links http://<build_ip>:8088/ --trusted-host <build_ip> pytest
```

Optional test reports:

- **pytest-html** (single-file self-contained HTML, most portable, generated by redeploy by default): on the DUT,
  add the pure-Python `pytest-html` + `pytest-metadata` (`--no-deps` avoids version mismatches from compiled
  extensions). Run `tools/run_report.sh` to produce `/tmp/report.html`. `tools/redeploy.sh` by default generates
  and pulls back the report to `~/test-reports/` every time (`NO_REPORT=1` skips).
- **Allure** (multi-file + interactive UI): install `allure-pytest` on the DUT (pure-Python wheel), and the allure
  CLI (Java) on the build machine. Run `tools/allure_report.sh` to collect and render.

## 2. Deploy + Run

```bash
# Build machine one-shot (package -> scp -> extract -> pytest)
tools/redeploy.sh "-m smoke -v"     # smoke first
tools/redeploy.sh "tests -v"        # everything
tools/redeploy.sh "-m l2 -v"        # a specific domain
```

Manual: `scp` the repo to the DUT, `cd` into it, and `sudo python3 -m pytest ...` (scapy needs root).

## 3. Smoke Must Pass First

`-m smoke` uses chip counters to confirm the hairpin loopback really returns frames to the pipeline (RX_PKT +~N).
If it doesn't pass, don't proceed; it's most likely one of:

- Port admin/oper down -> `config interface startup EthernetN`
- Loopback command syntax mismatch -> tune the `framework/loopback.py` template + `DUT_SDK`
- `EthernetN` <-> bcm port mapping mismatch -> set `DUT_BCM_PORT_PREFIX/OFFSET` or edit the profile's `bcm_port`

## 4. Platform Adaptation Switches (Environment Variables)

| Variable | Default | Description |
|------|------|------|
| `DUT_HOST` / `DUT_USERS` / `DUT_PASS` | see dutssh.py | Target device and login credentials (`DUT_USERS` comma-separated candidates, falls back to `DUT_USER`; default admin) |
| `DUT_SYNCD` | syncd | syncd container name |
| `DUT_SDK` | auto-detect | sdk6 / sdklt |
| `DUT_BCM_PORT_PREFIX` | cd | bcm port-name prefix |
| `DUT_BCM_PORT_OFFSET` | -1 | `EthernetN` -> `<prefix><N+offset>` |
| `DUT_DRY_RUN` | - | set to 1 to print only, not execute (build-machine self-check) |
| `DUT_TIMEOUT` | 180 | per-command timeout (seconds); raise for long tests (e.g. 1800) |

## 5. New-Device Onboarding

Probe-first throughout: confirm facts on the device before writing the profile.

### 5.1 Up-Front Information Gathering

```bash
show version                    # image branch/build
show platform summary           # platform / hwsku / ASIC
show interfaces status | head   # port naming (Ethernet starting index), default link mode
redis-cli -n 4 keys "VLAN|*"    # default VLAN
docker exec syncd ls /var/run/sswsyncd/ 2>/dev/null   # socket present => use socket diagnostics
docker exec syncd bcmcmd "show unit" 2>/dev/null      # echoes back => bcmcmd diagnostics available
config interface link-mode --help 2>/dev/null | head  # has bridge/route => route/bridge-style OS
```

### 5.2 Write the Device Profile (`topology/profiles.yaml`)

Add a section under `devices:` named by platform, filling in each field after confirmation (**every item must have
device-measured evidence**):

| Field | Meaning | How to confirm |
|------|------|----------|
| `default_vlan` | Default VLAN a port belongs to | `keys "VLAN\|*"` + `show vlan brief` |
| `bcm_port: {prefix, divisor, offset}` | `EthernetN` -> bcm port-name mapping | `ps` in the diagnostic shell cross-referenced with `show interfaces status` |
| `diag_access` | bcmcmd / socket | probe result from step 5.1 |
| `loopback_mode` | mac / phy | try `port <p> lb=mac`; if it doesn't take effect, use phy |
| `counter_prefix` | Counter-name prefix | observe via `show c <port>` |
| `caps` | Capability gating | each item needs evidence: whether the command group exists, whether `config <feature> enable` is rejected, whether the corresponding container exists. Declared unsupported -> false (structural skip); should be supported but broken -> true (let the case FAIL) |
| `copp` | Trap expectations | the measured enabled set in STATE_DB `COPP_TRAP_TABLE` |

### 5.3 Smoke Order (advance to the next step only after the current one passes)

1. `test_loopback_smoke.py`: loopback really returns frames to the pipeline (chip counter +N). On failure, check
   `loopback_mode` / `bcm_port` mapping first.
2. `test_vlan.py` + `test_port_counters.py`: VLAN semantics + counter reading (clear -> traffic -> read once).
3. `test_fdb.py` + `test_fdb_chip.py`: static/dynamic FDB, directed vs flooding.
4. `test_l3_forward_traffic.py`: L3 end-to-end.
5. Full `tests/` (nohup background + log polling).

Common after a factory reset: pytest missing (install offline per section 1), system clock behind (fix time with
`date` first).

## 6. Fault Recovery

- **Residual loopback**: `docker exec syncd bcmcmd 'port <bcm> lb=none'`, or rerun any case (the fixture cleans up
  as a fallback).
- **Suspected storm**: check for a looping topology where "re-entered frames get forwarded back to the loopback
  port" (a directed dst resolving to the loopback port itself, or a flood domain that includes the loopback port
  bouncing back and forth); check whether isolation PVID / flood_safe was missed; check whether mirror-to-cpu is
  leaking; a teardown that turns off loopback can stop it.
- **Configuration got scrambled**: `config reload <baseline snapshot config_guard saved on entry> -y -f`.

### Quick Troubleshooting Reference

| Symptom | Check first |
|------|------|
| Manual command passes, framework doesn't | the `_fixup` rewrite in `framework/cli.py` (probe match too broad/too narrow) |
| L2 suddenly all dead mid full-run | whether ports dropped out of the default VLAN; FDB/NEIGH residue in CONFIG_DB blocking the move |
| `show counters` always 0 | chip-level clear causing readback wraparound, or a stale snapshot swallowing the delta; switch to clear -> traffic -> read once |
| Flooding-class TX=0 | egress not oper-up (reading TX requires loopback to bring it up); use flood_safe instead of raw loopback |
| Config commands mass "Data Loading Failed" | whole-DB YANG validation broken by a dangling reference (check whether the default QoS map got wiped) |
| Intermittent SSH "auth failed" | dutssh command timed out (set `DUT_TIMEOUT` for long tests), not an authentication problem |
